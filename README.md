# Poker Club Golf Invitational

A public-facing tournament website for a tiered, match-play golf championship
run for a local poker club. 32 golfers, four skill tiers, a two-phase draft
system, and a bracket that cuts the field in half twice before a 4v4
championship. No handicap strokes — the draft is what keeps things fair.

The site is the **official system of record** for the tournament: rosters,
pairings, matchups, scores, advancement, eliminations, and the prize pool all
live here and are edited by a single tournament administrator. Players don't
need accounts.

## Quick start

Requires Node.js 20.9+ (developed against Node 24) and a Neon Postgres
database (see [Database](#database) — it's free and takes about a minute).

```bash
npm install
cp .env.example .env
# edit .env — set DATABASE_URL to your Neon connection string,
# and pick ADMIN_PASSWORD / SESSION_SECRET (see "Environment variables" below)
npm run db:migrate   # applies migrations to that database
npm run db:seed      # populates it with a full 32-player demo tournament
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). The public site is
immediately populated with a realistic mid-Round-1 snapshot from the seed
script. To manage it, sign in at
[http://localhost:3000/admin](http://localhost:3000/admin) with whatever
`ADMIN_PASSWORD` you set in `.env`.

## Architecture & key decisions

This section exists so a future maintainer (including future-you) doesn't
have to reverse-engineer *why* something was built a particular way.

### Next.js 16 is genuinely different from what you might expect

This project was built against Next.js 16, which shipped real breaking
changes after most public tutorials and training data were written:
`middleware.ts` is now `proxy.ts`, `next.config.ts`'s `eslint` option is
gone, and — most importantly for this app — **Prisma reads are not
recognized as a "dynamic API"** the way `cookies()`/`headers()` are. Without
intervention, `next build` would happily prerender every page once at build
time and freeze that snapshot, silently hiding every admin edit made
afterward. `app/layout.tsx` sets `export const dynamic = "force-dynamic"` at
the true root specifically to prevent this — the whole site renders fresh on
every request. Verified by checking `next build`'s route table: every route
is marked `ƒ` (dynamic), none are `○` (static).

If you're extending this app, skim `node_modules/next/dist/docs/` before
assuming a pattern from memory still applies — an `AGENTS.md`/`CLAUDE.md`
pair is regenerated by `next dev` specifically to flag this.

### Server Actions, not a REST API

Every mutation — admin CRUD, score entry, round advancement, the public
course-selection tool — is a [Server Action](https://nextjs.org/docs/app/getting-started/mutating-data)
in `lib/actions/*.ts`, not a hand-rolled `app/api/*` route handler. This is
the pattern Next 16's own docs now lead with, and it means less boilerplate:
no manual `fetch()` + JSON (de)serialization on the client, and forms work
with JavaScript disabled via progressive enhancement.

### Two-layer admin auth

A single shared password (`ADMIN_PASSWORD`) protects everything under
`/admin`. On success, a signed cookie is set (HMAC-SHA256 over an expiry
timestamp, via the Web Crypto API — no session table, no per-player
accounts). Two layers check it, matching Next's own security guidance
("Proxy should not be your only line of defense"):

1. **`proxy.ts`** — a fast, cookie-only check that redirects unauthenticated
   page loads away from `/admin/*`. This is the *optimistic* check.
2. **`lib/dal.ts`'s `requireAdminSession()`** — called at the top of every
   admin Server Action. This is the *real* authorization check, since Server
   Actions can be POSTed directly and shouldn't rely solely on page-level
   gating having run first.

The password is compared with a constant-time comparison (`lib/auth.ts`) so
response timing can't be used to brute-force it character by character.

### Data model

Every entity hangs off `Tournament`, so **running a 2027 season later is a
new `Tournament` row, not a rebuild** — the schema was designed for that from
day one, even though only one season's UI is built right now.

A few choices worth knowing about (see `prisma/schema.prisma` for the full
picture and inline reasoning):

- **No Prisma `enum`s**, even though the schema now runs on Postgres (which
  does support them) everywhere. This was originally a portability
  decision, back when the plan was SQLite locally / Postgres in production
  and SQLite's connector has no enum support (see [Database](#database)
  for why that plan changed) — but the convention stuck because it costs
  nothing and every "closed set of strings" field (statuses, formats,
  winners) already has a single TypeScript source of truth as a plain
  `String` column, validated against a union exported from
  `lib/constants.ts`. That's also the single source of truth for every
  dropdown and status label in the app.
- **Money is integer cents**, never floats, to avoid rounding drift. UI
  formats cents to dollars (`lib/format.ts`); admin forms take dollar input
  and convert on submit.
- **`TeamMembership` and `Pairing` are scoped to a `Round`, not a `Player`.**
  Players get completely redrafted every round — Round 1's "Team A" and
  Round 2's "Team A" are different `Team` rows with different rosters, even
  though they share a display name.
- **`MatchParticipant`** is a uniform join table (`matchId`, `playerId`,
  `side`) that scales from 1v1 (championship singles) to 2v2 (every other
  match) to 4v4 (sudden-death tiebreaker) without nullable player-slot
  columns on `Match` itself. `Pairing` is kept as a *separate*, real entity
  (not derived) for Round 1/2, since "teams privately build 2-man pairings"
  is a distinct, meaningful phase of the tournament the admin needs to
  record — but championship matches are built by picking individual players
  directly, since a locked 2-man pairing isn't really the right abstraction
  once teams are down to 4 players.
- **`MatchSegment` is deliberately generic** (`name`, `format`, `holes`,
  `pointsAvailable`, `winner`, raw scores) rather than hardcoded
  front-9/back-9/overall columns. Round 1 and Round 2's formats are fixed by
  the rules, but the championship's format is explicitly called out in the
  spec as likely to evolve — `lib/segment-templates.ts` provides sensible
  defaults per round, and every field remains editable afterward from the
  match's admin page. Nothing about scoring is hardcoded into components.
- **Points are always derived, never stored redundantly.** `Match.winner`
  doesn't exist as a column — `lib/tournament-logic.ts`'s
  `calculateMatchTotals`/`determineWinner` compute it from segments on every
  read. One pure function, unit-tested, used everywhere a score is
  displayed (home, players, matches, admin) — there's no way for a stored
  "winner" field to drift out of sync with the segments that actually
  determine it.

### Database: Postgres everywhere, via Neon branching

The project started on SQLite for local dev (zero setup, no account needed)
with Postgres reserved for production, switched by a one-line
`datasource.provider` change. That works fine right up until you actually
need to *run* both — at that point maintaining two sets of migration
history (SQLite and Postgres generate genuinely different DDL for the same
schema.prisma; a SQLite-generated migration will not run against Postgres)
becomes its own maintenance burden for no real benefit anymore.

Once this project was actually deployed, it moved to **Postgres in both
places**, using [Neon](https://neon.tech)'s branching feature: one Neon
project, two branches —

- **`production`** (Neon's default branch) — the live database, whatever
  Vercel's `DATABASE_URL` environment variable points at.
- **`development`** — an isolated branch for local work, instant to create,
  free to reset. Your local `.env` points here.

Both branches share one migration history (`prisma/migrations/`), applied
with `npx prisma migrate dev` locally (development branch) and
`npx prisma migrate deploy` for production — see
[Deployment](#deployment). Because it's the same engine everywhere, there's
no provider divergence to think about at all, and `db-relations.test.ts`
(see [Testing](#testing)) exercises the exact same Postgres behavior the
live site runs on, not an approximation of it.

If you'd rather not use Neon: any Postgres works, including
[Supabase](https://supabase.com) — just skip the branching part and use two
separate databases (or projects) instead of two branches of one project.

### Why not the newest of everything

Two dependencies were deliberately pinned *below* the latest available
version, for reasons worth recording:

- **TypeScript 5.9, not the TS 7 native compiler.** TS 7 was resolvable via
  npm at the time this was built, but the wider tool chain (ESLint's
  TypeScript plugin, `tsx`, Prisma's generated types) is written against the
  TS 5.x API surface. Betting a maintainability-focused project on a
  brand-new major compiler version wasn't worth the risk.
- **ESLint 9, not ESLint 10.** `eslint-config-next@16.3.1`'s bundled
  `eslint-plugin-react@7.37.5` only declares support up to ESLint `^9.7`, and
  genuinely breaks on ESLint 10 (`context.getFilename is not a function` —
  a removed rule-context method). This is an upstream compatibility gap,
  confirmed by inspecting `eslint-plugin-react`'s own `package.json`, not a
  guess. Revisit this pin once `eslint-config-next` bumps its bundled
  `eslint-plugin-react`.

## Environment variables

Copy `.env.example` to `.env` and fill in real values. **Never commit
`.env`** — it's already gitignored.

| Variable | Required | Description |
| --- | --- | --- |
| `DATABASE_URL` | yes | Postgres connection string (use the pooled `-pooler` host). Your local `.env` should point at the Neon **development** branch; Vercel's Production environment variable should point at the **production** branch. Never the same value in both places. |
| `ADMIN_PASSWORD` | yes | Plaintext password checked server-side for `/admin` access. Pick something long — it's compared with a constant-time comparison, but only the password's strength stops brute-forcing. Use a different value locally vs. in production. |
| `SESSION_SECRET` | yes | Random secret used to sign the admin session cookie. Generate one with: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Use a different value locally vs. in production. |

None of these are ever sent to the browser — `ADMIN_PASSWORD` and
`SESSION_SECRET` are only read inside Server Actions, Proxy, and the DAL,
none of which bundle into client JavaScript.

## Database

### First-time setup

1. Create a free account at [neon.tech](https://neon.tech) (GitHub sign-in
   works) and create a project — this repo's was created via the Neon CLI
   (`neonctl projects create`), but the dashboard works identically.
2. Create a second branch off the default one, named `development`
   (dashboard: **Branches → Create branch**, or `neonctl branches create
   --name development`). You now have `production` (the default branch) and
   `development`.
3. Grab the **pooled** connection string for the `development` branch
   (dashboard: **Connect**, or `neonctl connection-string development
   --pooled`) and put it in your local `.env` as `DATABASE_URL`.
4. `npm run db:migrate` to apply the schema, then `npm run db:seed`.

### Local development

```bash
npm run db:migrate    # apply pending migrations to whatever DATABASE_URL points at
npm run db:seed       # wipe and repopulate with the demo tournament
npm run db:studio     # open Prisma Studio, a GUI for browsing/editing data
```

`npm run db:seed` (see `prisma/seed.ts`) creates:

- A full 32-player field across 4 tiers (`Player 01`–`Player 32`), with
  placeholder hometowns and tier-correlated handicap indexes.
- 6 approved courses (one deliberately marked inactive, to exercise that
  state).
- A complete Round 1 draft: two 16-player teams, captains, all 8 pairings
  per team (paired tier-1-with-tier-4 and tier-2-with-tier-3, a simple
  balance heuristic), and **7 of the 8 possible matches** — one pairing per
  team is deliberately left unmatched, to demonstrate the alternating
  matchmaking process still being mid-flight.
- Those 7 matches in a deliberate mix of states: 3 complete (including one
  that ends in a half-point tie, to show that math rendering), 1 in
  progress, 2 scheduled, and 1 mid-course-selection with 3 of 4 players
  having already submitted a pick.
- Empty `Round 2` and `Championship` rows, so their tabs render a correct
  "hasn't started yet" empty state rather than erroring.

Re-run `npm run db:seed` any time to reset to this exact snapshot — it's
fully idempotent (wipes all tournament data first).

### Migrations

Prisma migration history lives in `prisma/migrations/` and is shared by
both Neon branches. When you change `prisma/schema.prisma`:

```bash
npm run db:migrate -- --name describe_your_change
```

This applies the migration to whatever `DATABASE_URL` your `.env` points at
(the `development` branch, normally) and creates a new migration file —
commit that file. Once you're happy with the change, apply the exact same
migration to production:

```bash
DATABASE_URL="<production-pooled-connection-string>" npx prisma migrate deploy
```

`migrate deploy` (unlike `migrate dev`) never prompts and never resets data
— it's the only migration command that should ever touch production.

## Admin guide

Sign in at `/admin/login`. Session lasts 7 days. The admin nav is
deliberately styled distinctly from the public site (dark, utilitarian) so
it never gets confused for a public page.

**Recommended order of operations for a new tournament:**

1. **Tournament** (`/admin/tournament`) — set the name, subtitle, season,
   description, and initial status (`Registration`). Prize pool and entry
   fee can stay blank until finalized.
2. **Players** (`/admin/players`) — add all registrants and assign their
   tier. Players can only be *removed* while the tournament is still in
   `Registration` — after that, mistakes are fixed by editing rather than
   deleting, since a player might already be referenced by a team or match.
3. **Courses** (`/admin/courses`) — add every course you'd consider
   approving. Toggle a course inactive rather than deleting it once it's
   been used in a match (deleting a referenced course is blocked
   automatically).
4. **Rounds & Matches** (`/admin/rounds`) — click into **Round 1** and work
   top to bottom:
   1. **Draft Teams** — "Start Draft" creates empty Team A / Team B, then
      the roster tool lets you tap each eligible player onto a side. A live
      per-tier tally (e.g. "Tier 2: 4/4") shows when the draft is balanced.
      Set each team's name and captain below the grid.
   2. **Pairings** — for each team, pick two unpaired players and add the
      pair. Lock/unlock and delete are available per pairing.
   3. **Matchups** — "Create Match" has two modes: **From Pairings** (pick
      one unmatched pairing from each team — the normal Round 1/2 flow) and
      **Pick Players** (check individual players directly — used for the
      championship's team/singles matches, and for a captain-vs-captain
      playoff in any round). Each mode pre-fills sensible default scoring
      segments for the match, which you can freely edit afterward.
   4. Click **Edit** on any match to set its course, scheduled date,
      status, Golf GameBook links, and — the important part — each
      segment's winner and score. Segment names, formats, and point values
      are all editable per match, not just per round, so the championship's
      format can change without touching code.
   5. **Finish Round** — once every match (or a recorded captain playoff)
      resolves the tie, **Complete Round & Advance** eliminates the losing
      team's players (marking them, not deleting them) and flips the round
      to `Complete`. For the championship specifically, this instead crowns
      the winning team's 4 players `Champion` and marks the tournament
      `Complete`.
5. Repeat for **Round 2** and the **Championship** — each round's roster
   tool automatically limits the eligible pool to players who weren't
   eliminated in an earlier round.
6. **Course Selection** (the public `/courses` page) doesn't need an admin
   step — once a match exists without a course assigned, it automatically
   appears there for the four players to pick from and randomize.

Every admin mutation calls `revalidatePath("/", "layout")`, so public pages
reflect changes immediately — there's no cache to bust or redeploy to
trigger.

## Testing

```bash
npm test          # run once
npm run test:watch
```

Two suites, both under `tests/`:

- **`tournament-logic.test.ts`** — pure-function unit tests for
  `lib/tournament-logic.ts`: segment point math (including ties splitting a
  point evenly), match/round totals matching the rules' own worked examples,
  round-advancement logic (including the "tied, no playoff yet" and
  "resolved by playoff" states), prize-per-player math with missing/zero
  values, and the weighted course randomizer — including the exact example
  from the spec (`A, A, B, C` → a 4-entry pool, ~50% draw chance for `A`,
  verified both by exact index and by a 4,000-trial statistical check).
- **`db-relations.test.ts`** — integration tests against the real Postgres
  database (whatever `DATABASE_URL` points at — the Neon `development`
  branch in normal use), covering the relational guarantees pure functions
  can't see: a player can belong to different teams in different rounds
  (redraft support), a round's roster query is correctly scoped to that
  round only, eliminated/champion players remain queryable with their
  history intact, and pairings are correctly scoped to their team and
  round. Every tournament these tests create is tagged `season: 2099`,
  which `afterAll` deletes — nothing lingers in the shared dev database
  between runs. This suite is what caught a real bug during development:
  `Pairing`/`MatchParticipant`/`CourseSelection`'s foreign keys to `Player`
  had no explicit `onDelete` behavior, which defaults to blocking the
  delete on Postgres — fixed by making them cascade (see the schema's
  top-of-file comments for the full reasoning).

Every one of these was chosen to match the spec's explicit testing
checklist (team membership is round-specific, players can be redrafted,
eliminated players remain in history, pairings belong to the correct
team/round, match points total correctly, ties can be represented, the
course randomizer weights duplicates properly, championship status works,
prize calculations don't break with missing values).

Beyond automated tests, the full tournament lifecycle — draft, pairings,
matchups, scoring, round completion and elimination, redraft, championship,
crowning champions — was manually driven end-to-end through the real admin
UI in a headless browser during development, then the database was reseeded
back to the demo snapshot described above.

## Deployment

Live on **Vercel + Neon Postgres**. This is how it's actually set up (not
just a suggested path):

1. **Database**: one Neon project with a `production` branch (the default)
   and a `development` branch, as described in [Database](#database).
2. **Vercel project**: `vercel link` from the repo root creates/links a
   Vercel project. `vercel git connect` (or the "Connect to Git" button in
   the Vercel dashboard) hooks it up to this GitHub repo for
   deploy-on-push — that step requires a one-time interactive GitHub
   authorization in Vercel's own dashboard (**Account Settings → Login
   Connections**) before it'll succeed; without it, deploys are triggered
   manually with `vercel --prod` instead of automatically on push.
3. **Environment variables**, set per-environment via `vercel env add
   <NAME> production` (or the dashboard): `DATABASE_URL` (the
   **production** Neon branch's pooled connection string —
   *not* the same one your local `.env` uses), `ADMIN_PASSWORD`, and
   `SESSION_SECRET`. Use different values than your local `.env` for the
   latter two.
4. **`.vercelignore`** excludes `.env`/`.env.local` explicitly. This
   matters: `vercel deploy` uploads local files independently of
   `.gitignore`, so without it your local `.env` — pointed at the
   *development* database, with dev-only secrets — would ride along into
   the deployment and could take precedence over the environment variables
   you configured in Vercel. Confirmed by testing: the first deploy here
   did exactly that, logging in with the local dev password instead of the
   production one, until `.vercelignore` was added.
5. Apply migrations to the production branch once (see
   [Migrations](#migrations)), then deploy: `vercel --prod`.

Because every page is rendered dynamically (see
[Architecture](#architecture--key-decisions)), admin edits made after
deployment show up immediately — there's no build step to re-trigger and no
risk of tournament data disappearing on redeploy or server restart.

Players never need Neon or Vercel accounts — only the admin's Server
Actions ever write to the database, gated by `ADMIN_PASSWORD`.

## Known limitations / roadmap

Documented honestly, since this is meant to be maintained past this initial
build:

- **The live turn-by-turn "alternating matchmaking" and snake draft aren't
  simulated in the UI.** Captains still work that negotiation out
  in person; the admin records the *result* (who got paired against whom,
  who ended up on which team) rather than the site running a live draft
  board. This was a deliberate scope decision — the site's job is to be the
  system of record, not to replace the room where the draft happens.
- **No player photo/avatar upload flow.** The schema has an `avatarUrl`
  field ready for it, but there's no image hosting wired up — the field is
  currently unused. Course images (`Course.imageUrl`) are in the same
  state.
- **No multi-tournament UI.** The database fully supports it (every entity
  hangs off a `Tournament` id), but there's currently no admin screen to
  create a new season or switch which tournament is `isActive` — that's a
  direct SQL/Prisma Studio operation for now. Worth a small admin screen
  once a second season actually happens.
- **No automated email/SMS notifications** when a match is scheduled or a
  round completes — players are expected to check the site.
- **Golf GameBook integration is link-only**, as specified: this site
  stores and surfaces the URLs but doesn't pull live scores from GameBook's
  API. If GameBook (or another provider) exposes a scoring API later, the
  natural integration point is `Match.externalScoringUrl` and the
  `MatchSegment` scoring fields.
